# Lab 3 — Gestion des réservations avec JPA

Ce projet permet de comprendre comment JPA et Hibernate enregistrent des utilisateurs, des salles, des réservations et des équipements dans une base H2. La classe `App` teste les associations, les cascades et les suppressions, puis affiche les résultats dans la console.

## Lancer le projet

Il faut un JDK 8 ou supérieur et Maven. La base H2 fonctionne en mémoire : aucune installation de serveur de base de données n'est nécessaire.

```bash
mvn test
mvn compile org.codehaus.mojo:exec-maven-plugin:3.5.0:java -Dexec.mainClass=com.example.App
```

On peut aussi lancer directement la méthode `main` de `App` depuis IntelliJ IDEA.

## Les entités et leurs relations

| Entité | Rôle | Relations |
|---|---|---|
| `Utilisateur` | Possède un nom et un email unique. | Un utilisateur peut avoir plusieurs réservations. |
| `Salle` | Possède un nom et une capacité. | Une salle peut avoir plusieurs réservations et plusieurs équipements. |
| `Reservation` | Définit une date de début et une date de fin. | Chaque réservation appartient à un utilisateur et à une salle. |
| `Equipement` | Possède un nom unique, par exemple « Projecteur ». | Un équipement peut être associé à plusieurs salles. |

`Reservation` porte les clés étrangères `utilisateur_id` et `salle_id`. La relation entre les salles et les équipements utilise la table de jointure `salle_equipement`.

Les méthodes `addReservation`, `removeReservation` et `addEquipement` mettent à jour les deux côtés des associations en mémoire.

## Analyse des logs SQL générés

Les captures ci-dessous montrent des étapes du développement. Les exemples SQL sont simplifiés pour faciliter la lecture ; Hibernate ajoute des alias dans les logs réels.

### 1. Création des tables

![Création des tables par Hibernate](docs/images/creation-tables.jpg)

Au démarrage, Hibernate lit les annotations des entités et crée les tables manquantes. Le projet utilise `hibernate.hbm2ddl.auto=update` dans `persistence.xml`.

**Table `Equipement`**

```sql
create table Equipement (
    id bigint generated by default as identity,
    nom varchar(255) not null,
    primary key (id)
);
```

Cette table stocke les équipements. `identity` génère automatiquement l'identifiant, `not null` rend le nom obligatoire et `primary key` identifie chaque ligne. L'unicité du nom est ajoutée par une contrainte distincte, qui n'est pas visible dans cet extrait.

**Table `Reservation`**

```sql
create table Reservation (
    id bigint generated by default as identity,
    dateDebut timestamp not null,
    dateFin timestamp not null,
    salle_id bigint not null,
    utilisateur_id bigint not null,
    primary key (id)
);
```

`timestamp` stocke la date et l'heure. `salle_id` et `utilisateur_id` indiquent la salle et l'utilisateur concernés. Hibernate ajoute ensuite les contraintes de clés étrangères. Une réservation doit avoir ses deux dates, sa salle et son utilisateur.

**Table `Salle`**

```sql
create table Salle (
    id bigint generated by default as identity,
    capacite integer not null,
    nom varchar(255) not null,
    primary key (id)
);
```

Cette table enregistre le nom et la capacité de chaque salle. La capacité est un entier et le nom est une chaîne de caractères.

**Table `salle_equipement`**

```sql
create table salle_equipement (
    salle_id bigint not null,
    equipement_id bigint not null,
    primary key (salle_id, equipement_id)
);
```

Chaque ligne relie une salle à un équipement. La clé primaire composée empêche d'enregistrer deux fois le même lien. Un équipement peut ainsi être partagé sans dupliquer sa ligne dans `Equipement`.

La table `Utilisateur`, créée elle aussi au démarrage, n'apparaît pas dans cette capture.

### 2. Retrait d'une réservation : `orphanRemoval`

![Lecture et suppression d'une réservation](docs/images/suppression-reservation.jpg)

La capture montre trois opérations successives.

```sql
select * from Reservation where salle_id = ?;
```

Hibernate charge les réservations de la salle. Le symbole `?` représente un paramètre dont la valeur est fournie au moment de l'exécution.

```sql
delete from Reservation where id = ?;
```

La réservation retirée de la collection est supprimée en base grâce à `orphanRemoval = true`. Il n'est pas nécessaire d'appeler `em.remove(reservation)` dans ce cas.

```sql
select * from Reservation where id = ?;
```

L'application recherche ensuite cette réservation pour vérifier la suppression. Aucune ligne n'est trouvée : `em.find(...)` retourne `null`.

Les noms comme `reservatio0_` et `id1_1_0_` sont des alias générés par Hibernate pour lire les résultats. Ils ne représentent pas de nouvelles tables.

### 3. Résultat après suppression d'une salle

![Comptage des entités après suppression de la salle](docs/images/resultats-suppression-salle.jpg)

```sql
select count(id) from Utilisateur;
select count(id) from Salle;
select count(id) from Reservation;
select count(id) from Equipement;
```

Chaque requête compte les lignes restantes dans une table. Dans cette capture, la console affiche :

```text
Utilisateurs : 1, salles : 0, reservations : 0, equipements : 1
```

La salle et ses réservations ont été supprimées. L'utilisateur existe toujours, ainsi que le projecteur. La cascade `ALL` de `Salle` vers ses réservations inclut `REMOVE`. La relation vers les équipements utilise seulement `PERSIST` et `MERGE`, donc le projecteur est conservé.

Cette capture correspond à la version qui supprimait directement la salle. Dans la version actuelle de `App`, on supprime d'abord l'utilisateur et sa réservation restante, puis la salle. Le résultat final est donc différent :

| Étape actuelle dans `App` | Utilisateurs | Salles | Réservations | Équipements |
|---|---:|---:|---:|---:|
| Après persistance | 1 | 1 | 2 | 1 |
| Après retrait d'une réservation | 1 | 1 | 1 | 1 |
| Après suppression de l'utilisateur | 0 | 1 | 0 | 1 |
| Après suppression de la salle | 0 | 0 | 0 | 1 |

## Comprendre les cascades

- `em.persist(salle)` enregistre la salle et son nouvel équipement grâce à `PERSIST`.
- `em.persist(user)` enregistre l'utilisateur et ses réservations grâce à `ALL`.
- `em.remove(user)` supprime l'utilisateur et ses réservations, mais conserve la salle.
- Supprimer une salle peut supprimer ses réservations, mais conserve les équipements.

La salle doit être persistée avant l'utilisateur dans cet exemple : aucune cascade n'est définie de `Reservation` vers `Salle`.

Les cascades décrites ici sont exécutées par Hibernate ; elles ne correspondent pas à une configuration SQL `ON DELETE CASCADE`.

## Validations et requêtes JPQL

`Reservation.verifierDates()` vérifie les dates avant une insertion ou une mise à jour. Elles doivent être renseignées et le début doit être strictement avant la fin.

`ReservationService` propose trois méthodes :

| Méthode | Résultat |
|---|---|
| `estSalleDisponible(salleId, debut, fin)` | Vérifie qu'aucune réservation ne chevauche la période demandée. |
| `reservationsUtilisateur(utilisateurId)` | Retourne les réservations de l'utilisateur, triées par date de début. |
| `sallesAvecEquipement(nomEquipement)` | Retourne les salles associées à cet équipement. |

Une réservation de 10 h à 11 h bloque cette période, mais autorise une nouvelle réservation à partir de 11 h. La méthode consulte la disponibilité ; elle ne bloque pas automatiquement l'enregistrement de réservations simultanées.

En cas d'erreur dans `App`, la transaction en cours est annulée avec `rollback()`. Le message d'erreur est affiché et les ressources JPA sont fermées dans `finally`.
